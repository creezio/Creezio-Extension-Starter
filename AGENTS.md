# Instructions de développement du starter Creezio

Ce dépôt prépare `creezio.purchase-requests` 0.1.4 : un module métier installable et sa partie plugin conversationnel. La démo persistante conserve sa version installée jusqu'à une transition explicite. Le module reste utilisable sans chat. Le code importe le SDK public distribué (`@creezio/sdk`) et ses autres dépendances déclarées ; aucun import relatif vers un checkout Creezio, composant privé, accès SQL libre ou secret d'hôte. Le pin public SDK 1.2 de cette candidate est fixé dans `ci/sdk-pin.json` ; la publication du module reste distincte de la qualification de ses sources et archives.

Référence normative publique fixée pour cette tranche : [Creezio-D1R2 `e67636635a526daa544ea3573b271e1822f3f4fe`](https://github.com/creezio/Creezio-D1R2/tree/e67636635a526daa544ea3573b271e1822f3f4fe). Lire selon le changement le [standard de module](https://github.com/creezio/Creezio-D1R2/blob/e67636635a526daa544ea3573b271e1822f3f4fe/docs/STANDARD-MODULE.md), le [standard de développement](https://github.com/creezio/Creezio-D1R2/blob/e67636635a526daa544ea3573b271e1822f3f4fe/docs/DEVELOPMENT-STANDARD.md), les [dépendances de modules](https://github.com/creezio/Creezio-D1R2/blob/e67636635a526daa544ea3573b271e1822f3f4fe/docs/DEPENDANCES-MODULES.md) et les [interactions des widgets](https://github.com/creezio/Creezio-D1R2/blob/e67636635a526daa544ea3573b271e1822f3f4fe/docs/INTERACTIONS-WIDGETS.md). Ces liens décrivent le contrat public à cette révision ; ils ne sont ni des imports ni une preuve que des capacités ultérieures existent. Les guides locaux du starter sont indexés dans [skills/README.md](skills/README.md).

Lire `README.md`, `prd.md`, `interview.md`, `TODO.md`, `FILES.md`, `module/public-contract.ts` et `module/generate-manifest.mjs` avant une modification métier. Garder un seul contrat d'opérations pour UI, API et MCP. Résoudre acteur, audience et contexte côté hôte ; les handlers limitent toujours les demandes au principal et au contexte du port. La catégorie privée de fichiers déclare `ownerScope: principal` pour partager un fichier du même propriétaire entre `admin` et `app` sous les droits de chaque audience ; ce scope ne dispense jamais du contrôle du contexte. Les mutations portent `requestKey`, les mises à jour leur révision attendue. `attachment.link` publie le fichier staged, crée le lien et incrémente la révision dans le même lot. Le modèle déclare l'état courant ; la création et l'évolution D1 relèvent de la chaîne centrale de Creezio, sans migration dans ce module.

Les vues workspace/front utilisent les primitives SDK publiques et conservent les panneaux de l'interface d'origine. Les widgets MCP Apps n'exécutent aucun effet métier au rendu : get/list directs sont des lectures ; un message exige un envoi volontaire ; le contexte du prochain tour est limité à l'identifiant, au titre et à la révision. Soumettre une demande n'effectue ni achat ni approbation budgétaire. Les mêmes droits serveur s'appliquent à chaque canal.

Maintenir les documents touchés (`README`, PRD, décisions, TODO, changelog, FILES), le manifeste généré et les six suites réelles `backend`, `ui`, `api-mcp`, `widgets`, `package`, `docs`. Le manifeste et `dist/` sont des sorties ignorées : la provenance Git et l'intégrité source proviennent du commit exact ; les archives runtime et validation restent séparées. Vérifier les octets du paquet et son installation dans un hôte indépendant avant d'annoncer une release ; tests du module, navigateur, Sites, Cloudflare et ChatGPT sont des preuves distinctes. Ne jamais inclure dans le paquet secrets, données de démo, sources privées du socle ou scripts SQL de transformation.

Préserver sources, données et états existants. Réutiliser checkout, dépendances et répertoire de compilation ; vérifier l'espace libre avant une opération volumineuse. Nettoyer seulement les temporaires créés et devenus inutiles, après vérification qu'aucun processus ne les utilise.
